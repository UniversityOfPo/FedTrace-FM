# FedTrace External Baseline Selection Plan

**Status:** Planning/literature-selection document only. No code, config, test, README, Research Database, or existing research-plan/analysis file was created or modified in producing it. No experiment was run. FedTrace v3 remains frozen and untouched. This document decides *which* external baseline(s) are scientifically fair, implementable, and publication-relevant — it does not implement any of them.

---

## 1. Define the Comparison Problem

FedTrace v3 (`src/analysis/fedtrace_detector.py`, frozen per `research_plans/FEDTRACE_V3_TEMPORAL_RESIDUAL_CALIBRATION_PLAN.md`) outputs, per run:

- a **suspicious client identity** (`predicted_client` — the earliest-confirmed client under the frozen tie-breaking rule),
- an **attack onset estimate** (the first round of the confirmed persistent anomalous run),
- a **per-client-round anomaly score** (`FedTraceV3Score(k,r) = max(z_m, z_t_res)`),
- a **persistent confirmation** (requiring `P=3` consecutive anomalous rounds before acting), and
- **attack-agnostic coverage** across both a magnitude-revealing signal (`z_m`) and a norm-preserving-attack-revealing signal (`z_t_res`), combined without knowing the attack type in advance (`analysis/FEDTRACE_STAGE_B_FINAL_SYNTHESIS.md` §8).

This is fundamentally an **attribution / anomaly-detection task**: *which* client, *when*. It is explicitly **not** an aggregation-robustness task — FedTrace v3 never modifies `AggregationStrategy` or the global model; it is a purely offline, post-hoc detector applied to an already-completed run's trace (`src/federated/runner.py`'s `update_transform_callback` and `AggregationStrategy` plugin points are both untouched by it, confirmed by direct inspection of `src/federated/runner.py` and `src/federated/aggregation/base.py`).

**Two structurally different categories of external baseline therefore exist, and must not be conflated:**

- **(A) Attribution / anomaly-detection baselines** — methods whose native output is (or can reasonably be extracted as) a suspicious-client identity, a per-client anomaly score, or an onset estimate. These are the only baselines that answer the *same question* FedTrace v3 answers, and are the only ones eligible to be compared on FedTrace's own metrics (§9).
- **(B) Robust-aggregation baselines** — methods that modify the server's aggregation rule to *reduce global-model damage* from Byzantine/malicious clients, without necessarily identifying who is responsible or when they started. These answer a *different* question and must be evaluated on different metrics (§10) — comparing them to FedTrace on attribution metrics would be an invalid comparison (§8).

## 2. Baseline Candidate Categories

**A. Simple anomaly baselines** (update norm; cosine similarity; distance-to-mean/median-type rules; clustering/outlier scores). This project has **already implemented and exhaustively evaluated** the two most natural members of this category as FedTrace's own internal ablations: `update_l2_norm`-based magnitude-only detection (`z_m`) and a per-client peer-cosine baseline (`analysis/EXP_014_Gaussian_Attack_Traceability_Analysis.md` §4, and Detector A/B in every Stage A/B document). A generic, literature-only "distance-to-median" rule with no specific external citation would not add a genuinely *external* comparison point beyond what is already reported — it would only be a minor recalibration of an ablation already run. This category is therefore **not** pursued as a new external baseline on its own; a specific, citable, well-established instance of it (Multi-Krum's nearest-neighbor score, §4) is pursued instead, where it is a genuinely distinct, externally-sourced method, not a recombination of this project's own already-tested signals.

**B. Classical robust aggregation.**
- **Krum / Multi-Krum** (Blanchard, El Mhamdi, Guerraoui, Stainer, *"Machine Learning with Adversaries: Byzantine Tolerant Gradient Descent,"* NeurIPS 2017; arXiv:1703.02757). For each client, sums the squared Euclidean distances to its `n − f − 2` nearest-neighbor updates (where `f` is an assumed upper bound on the number of Byzantine clients); Krum selects the single client with the lowest such score as that round's entire update; Multi-Krum averages the `m` lowest-scoring clients' updates.
- **Coordinate-wise median / trimmed mean** (Yin, Chen, Ramchandran, Bartlett, *"Byzantine-Robust Distributed Learning: Towards Optimal Statistical Rates,"* ICML 2018; arXiv:1803.01498; proceedings: `https://proceedings.mlr.press/v80/yin18a.html`). Aggregates each model parameter independently across clients via the coordinate-wise median or a trimmed mean (discarding the highest/lowest `β` fraction of values per coordinate before averaging).

**C. Attribution-oriented / malicious-client-detection methods.**
- **FoolsGold** (Fung, Yoon, Beschastnikh, *"Mitigating Sybils in Federated Learning Poisoning,"* arXiv:1808.04866, 2018; extended as *"The Limitations of Federated Learning in Sybil Settings,"* RAID 2020). Computes pairwise cosine similarity between clients' *historical* (accumulated across rounds) update vectors and down-weights clients whose contributions are unusually similar to each other, on the premise that colluding Sybil/poisoning clients submit mutually similar updates while honest clients, even under heterogeneity, do not.

No candidate was included merely because it is popular (e.g. no attempt was made to force-fit a purely IID-assuming or purely image-classification-specific method that does not generalize to this project's federated-averaging, cross-silo, 5-client setting).

## 3. Fairness Criteria (Per Candidate)

| Criterion | Multi-Krum | Trimmed mean / median | FoolsGold |
|---|---|---|---|
| Identifies a client? | Yes — the excluded/lowest-selected client(s) each round, as a **repurposed** signal (not the paper's stated deliverable) | No — coordinate-wise, no client identity ever surfaces | Yes — a per-client weight, natively |
| Estimates attack onset? | Not natively; could be inferred from when exclusion becomes persistent (repurposed, same caveat as above) | No | Not natively; a weight-decay trajectory could be inspected, but the original paper does not define an onset rule |
| Only defends aggregation? | Primarily yes; attribution is a side-effect, not the design goal | Yes, exclusively | No — its stated goal is Sybil identification, aggregation weighting is downstream of that |
| Requires knowing the number of malicious clients (`f`)? | **Yes** — `f` (or an upper bound) is a required parameter of Krum/Multi-Krum's neighbor count | Requires the trim fraction `β`, functionally the same assumption | No explicit `f`; but its core mechanism assumes **multiple** colluding clients exist (see below) |
| Assumes IID or weak heterogeneity? | The original analysis assumes bounded gradient variance across honest clients; not proven for strong Non-IID (`α=0.1`) | Same caveat — coordinate-wise robustness guarantees are derived under bounded-variance assumptions, not validated under this project's already-documented strong Non-IID partition variance (`analysis/EXP_009_Three_Seed_Baseline_Analysis.md`) | Assumes honest clients are directionally diverse even under heterogeneity, which is at least directionally consistent with this project's own heterogeneity findings, but not validated at `α=0.1` by the original authors |
| Requires server-side trusted data? | No | No | No |
| Requires extra models or computation? | `O(n²·(d + log n))` pairwise distance computation per round over the full parameter vector (`d ≈ 11.2M` for this project's ResNet-18) — nontrivial but tractable at `n=5` | Coordinate-wise sort per parameter — tractable at `n=5` | Maintains a running historical similarity matrix per client pair; tractable at `n=5` |
| Compatible with 5 clients? | Yes, mechanically — but Krum's own resilience guarantee requires `n ≥ 2f + 3`; at `n=5` this permits at most `f=1`, which happens to match this project's exact one-malicious-client threat model | Same small-`n` fragility as Krum for the trim fraction `β` | Mechanically compatible; its *effectiveness* claim, not its computability, is the concern (below) |
| Meaningful under all-5-clients-selected-every-round participation? | Yes — this project's `clients_per_round=5=num_clients` setting is compatible with Krum's per-round neighbor computation | Yes | Yes |
| Meaningful for both Gaussian and norm-preserving directional attacks? | Krum's distance metric is Euclidean on raw parameters — plausibly sensitive to the Gaussian attack's magnitude perturbation; **unverified** whether it is sensitive to a norm-preserving, direction-only perturbation, since Euclidean distance does respond to direction changes even at constant norm (unlike a magnitude-only detector) — this is a genuine open question this plan does not resolve by assertion | Coordinate-wise median could plausibly be pulled by a directional attack in specific coordinates, but this is equally unverified | **Likely not meaningful for either attack family here**, because FoolsGold's mechanism specifically requires *multiple, mutually similar* malicious contributions to distinguish from honest diversity — with exactly one non-colluding attacker (this project's threat model, `research_plans/PHASE5_Malicious_Client_Traceability_Plan.md` §3), there is no second sybil for the lone attacker's updates to be "unusually similar to," removing the signal FoolsGold is built around |
| Can it be evaluated on the exact same `EXP_016`–`EXP_019` traces? | **No** — Krum's distance computation requires the *raw per-client model-update tensors*, which are never persisted to `client_round_trace.csv` (only scalar summaries — `update_l2_norm`, `peer_mean_cosine_similarity`, `self_prev_round_cosine` — are logged, confirmed directly against `src/attacks/traceability.py::TRACE_CSV_FIELDNAMES` and `analysis/PHASE5_Implementation_Verification.md`'s own prior finding that raw updates are never saved) | **No**, same reason | **No**, same reason (also needs the raw historical update vectors) |
| Would implementing it change the training protocol? | **Yes** — it must run *live*, as the actual `AggregationStrategy` during training (`src/federated/aggregation/base.py`'s `AggregationStrategy.aggregate(global_state, updates)` interface), because it determines what the *next* round's global model actually is; it cannot be computed retroactively from a FedAvg-aggregated run's already-fixed trajectory | Same — must run live as the aggregation rule | Native FoolsGold also modifies the *learning rate* applied per client during aggregation, so it too must run live |
| Apples-to-apples with FedTrace, or only complementary? | **Complementary on its native task** (aggregation robustness); attribution use is an explicit, clearly-labeled repurposing, not an apples-to-apples comparison on FedTrace's own terms | Purely complementary; no attribution comparison is possible at all | Would be apples-to-apples *if* its assumptions matched this project's threat model — they do not (above), so a direct metric-for-metric comparison would be scientifically misleading unless explicitly caveated as "evaluated outside its designed operating regime" |

**Architectural note, confirmed by direct code inspection (`src/federated/aggregation/base.py`, `src/federated/aggregation/fedavg.py`, `src/federated/runner.py`):** any of these three methods, as an `AggregationStrategy` subclass, would receive the full raw per-client `ClientUpdate.model_state` tensors natively — the existing plugin interface (`aggregate(global_state, updates)`) already exposes exactly what Krum/trimmed-mean/FoolsGold need, with no change required to `FederatedClient`, `FederatedServer`, `FederatedRunner`, or the attack-injection hook (`update_transform_callback`). Implementation is therefore architecturally clean; the obstacle is not code complexity but the fact that **any of them requires a new set of training runs**, not an offline analysis (§7).

## 4. Primary vs. Secondary Baselines

**Primary: Multi-Krum**, used two ways, each explicitly labeled by which question it answers:
1. **Natively**, as a robust-aggregation comparison (§10 metrics) — does it reduce global-model damage relative to attacked FedAvg, for either attack family, and at what cost to clean (honest-run) performance?
2. **As a clearly-labeled, secondary, repurposed attribution proxy** (§9 metrics, reported separately and never merged into FedTrace's own attribution table) — does the pattern of which client Multi-Krum excludes, round over round, converge on `client_002`, and if so, how does its (best-effort, not designed-for-this) onset estimate compare to FedTrace v3's?

**Secondary (documented, not selected for implementation now): coordinate-wise median / trimmed mean** (Yin et al.) — retained as a documented, viable second robust-aggregation comparison for a *future* task if reviewers specifically ask for more than one aggregation baseline, but **not** implemented alongside Multi-Krum now, per the explicit instruction to avoid recommending many baselines for completeness (§13).

**FoolsGold was considered and explicitly rejected as a baseline for this benchmark** — not omitted silently. Its core mechanism requires multiple, mutually-similar colluding malicious clients to distinguish from honest diversity; this project's entire attack series (`EXP_014`–`EXP_019`) uses exactly one, non-colluding malicious client by design (`research_plans/PHASE5_Malicious_Client_Traceability_Plan.md` §3's single-attacker scope). Running FoolsGold against a single-attacker scenario would very likely produce a degenerate or uninformative result not attributable to any real weakness of the method — that would be an unfair test of FoolsGold, not a fair comparison to FedTrace, and this plan declines to construct one on that basis. **This is itself a decision, not an evasion**: it demonstrates that the "one clean external attribution baseline" search was performed honestly rather than settled on the first available paper with the word "detection" in its title.

## 6. FedTrace-Specific Evaluation Question — "Which Client, and When?"

- **Multi-Krum:** Partially. Attacker identity could be extracted as the client most frequently excluded (Krum) or assigned the lowest score (Multi-Krum) once selection becomes consistently one-sided, but this requires defining a *new*, not-in-the-original-paper persistence rule (analogous to FedTrace's own `P=3`) to distinguish a genuine pattern from round-to-round noise in the selection — this plan does not invent that rule now (§13: no implementation in this task). Onset would be extracted as the first round of that (not-yet-defined) persistent exclusion pattern. **This is not a native capability and must be presented as such if pursued.**
- **Trimmed mean / coordinate-wise median:** **No.** No client identity is ever exposed by this method at any stage — every coordinate is aggregated independently and no per-client record of contribution is retained. Not a direct attribution baseline under any repurposing.
- **FoolsGold:** **Yes, in principle** — the per-client weight *is* a suspiciousness score, and a client whose weight collapses first could be read as an onset estimate. **But not for this benchmark specifically** (§4): with a single non-colluding attacker, the mechanism FoolsGold relies on to separate "suspicious" from "honestly diverse" has no basis to activate correctly, so even though the method *would* answer the same question as FedTrace in a multi-attacker setting, it cannot be expected to do so fairly here.

## 7. Trace-Only vs. New-Run Baselines

**None of the three shortlisted candidates can be evaluated offline from the already-collected `client_round_trace.csv` files.** All three require either the raw per-client model-update tensors (never persisted — confirmed directly against `TRACE_CSV_FIELDNAMES` in `src/attacks/traceability.py`) or must run live as the actual aggregation rule during training (confirmed directly against `src/federated/aggregation/base.py`'s interface and `src/federated/runner.py`'s aggregation call site, `run_round()` step 7). **This is the single most important practical finding of this plan**: unlike FedTrace v3 itself, whose entire Stage A/B validation was performed purely offline on already-collected traces, *any* of the three candidates in §2/§5 requires new experiment runs — new training, not new analysis. Per the instruction to prefer trace-only comparisons first where scientifically valid: **no trace-only-valid candidate exists** among the methods that are actually established, fairly-scoped external baselines for this problem; the choice in §11 is made with this constraint accepted, not avoided.

## 8. Avoiding Invalid Comparisons

Explicitly rejected as misleading, and not performed anywhere in this plan or any future baseline task built from it:

- **Claiming Multi-Krum is "worse" because it does not output an onset round.** It was never designed to; onset localization is not part of its stated contribution. Any onset comparison must be clearly marked as evaluating Multi-Krum *outside* its designed scope (§6), never presented as a fair like-for-like deficiency.
- **Claiming FedTrace is "better" on global-model accuracy** because it does not itself change aggregation. FedTrace has no accuracy-recovery mechanism at all (§17 of `analysis/FEDTRACE_STAGE_B_FINAL_SYNTHESIS.md`); comparing its (nonexistent) accuracy-recovery effect to Multi-Krum's actual one would be comparing a detector to a mitigation system, not two instances of the same task.
- **Comparing detector F1/precision/recall directly to aggregation-strategy test accuracy** without separating objectives. These belong to entirely different metric families (§9 vs. §10 below) and must never appear in the same comparison table without an explicit column separating which question each number answers.

**What belongs to the attribution comparison (§9):** predicted client, attribution correctness, first anomaly, confirmation round, onset estimate, onset error, detection delay, honest persistent FP, precision, recall, F1 — computed only for methods that produce a client-level output at all (natively or via an explicitly-labeled repurposing).

**What belongs to the robustness/mitigation comparison (§10):** final test loss, Top-1, Top-5, degradation relative to attacked FedAvg, clean-performance cost, any exposed client-selection/rejection pattern — computed only for methods that modify aggregation, evaluated against their own honest/attacked paired baselines, never against FedTrace's attribution metrics.

## 9. Metrics for Direct Attribution Baselines

For any candidate treated as an attribution baseline (Multi-Krum's repurposed signal, if pursued; any future genuine attribution method): predicted malicious client, attribution correctness, first anomaly, confirmation round (if the method has a persistence concept — Multi-Krum's would need one newly defined, §6), onset estimate, onset error, detection delay, honest persistent FP, precision, recall, F1 — using the exact same Stage B validation runs (`EXP_016`–`EXP_019`) FedTrace v3 was already evaluated on, once the required new experiment runs (§7) produce a comparable trace for each.

## 10. Metrics for Robust-Aggregation Baselines

For Multi-Krum (and, if later pursued, trimmed mean/median) evaluated on its native task: final test loss, Top-1, Top-5, recovery/degradation relative to attacked FedAvg (i.e. how much of `EXP_016`–`EXP_019`'s Top-1 gap vs. their paired honest baselines, `analysis/FEDTRACE_STAGE_B_FINAL_SYNTHESIS.md` §13, does Multi-Krum close), clean-performance cost (Multi-Krum run against the *honest* baseline configuration, i.e. no attack at all, to quantify any accuracy cost the robust rule imposes even absent an attacker — Krum in particular is known in the literature to underperform FedAvg on purely honest, heterogeneous data since it discards most clients' updates every round), and any exposed client-selection/rejection behavior (which client(s) Multi-Krum excluded, per round — logged as a byproduct, not forced into an attribution metric unless explicitly separated per §6/§8).

## 11. Selected Next Baseline Task

**B. Implementation of one robust-aggregation baseline: Multi-Krum**, as a new `AggregationStrategy` subclass, evaluated natively on its own robustness/mitigation metrics (§10) against the same four already-validated attack scenarios (`EXP_016`–`EXP_019`'s configurations, run with `aggregation: multikrum` in place of `fedavg`, everything else — seed, attack parameters, client set — held identical) plus their paired honest baselines, **and** — as an explicitly separate, clearly-labeled, secondary analysis, not merged into the primary result — its per-round exclusion pattern examined as a best-effort, out-of-native-scope attribution proxy (§9), with the caveat from §6 stated prominently wherever that secondary analysis is reported.

This is chosen over (A) because no genuinely fair, native attribution baseline survives the fairness screen in §3/§4 (FoolsGold rejected on threat-model grounds; Multi-Krum's attribution capability is real but secondary and requires a new persistence rule not yet defined). It is chosen over (C) because sufficient literature grounding already exists to proceed (§5) — the two flagged unverified details (Krum's exact resilience bound; whether an official trimmed-mean/median repository exists) are narrow, checkable-before-implementation items, not evidence that the broader landscape is under-researched.

## 12. Publication-Risk Justification

The Stage B synthesis (`analysis/FEDTRACE_STAGE_B_FINAL_SYNTHESIS.md` §20–21) already established that internal ablations (peer-cosine, magnitude-only, temporal-residual-only) and independent cross-seed validation (four PASS runs across two attack families) are both READY — the evidence package already answers "does FedTrace v3's own internal design make sense, and does it generalize to unseen seeds within its own family of comparisons." What it cannot yet answer is whether FedTrace v3's reported performance is meaningful **relative to any existing alternative a reviewer would already know about**. Multi-Krum is the single most-cited, most foundational Byzantine-robust aggregation baseline in this literature (§5) — a reviewer unfamiliar with the specific attribution problem this project studies will almost certainly ask "why not just use Krum?" **Answering that question directly — showing concretely what Krum does and does not provide on the exact same attack scenarios, including whether its own byproduct exclusion pattern comes anywhere close to the onset-exact, zero-honest-FP attribution FedTrace v3 already demonstrated — is the single highest-leverage piece of evidence available to close the gap the Stage B synthesis identified as highest priority.** It converts an internally-consistent result into one benchmarked, at least once, against the field's most standard reference point.

## 13. Scope Control

**Explicitly not recommended as part of this next step, or as an immediate follow-up to it:**

- **Five different robust aggregators.** Exactly one (Multi-Krum) is selected; trimmed mean/median remains documented but unimplemented (§4).
- **New attacks.** The same two already-validated, pre-registered attack transforms (`gaussian_update_noise`, `norm_preserving_directional`) are reused unchanged — no third attack family is introduced.
- **More seeds.** The same two already-validated seeds (123, 2026) are reused — no seed multiplication beyond what Stage B already established as sufficient for its own cross-seed criterion.
- **New models or datasets before external comparison.** CIFAR-100/ResNet-18/5-clients remains the evaluated configuration; broadening this is explicitly deferred until after the external-comparison gap is closed (`analysis/FEDTRACE_STAGE_B_FINAL_SYNTHESIS.md` §22 already states this discipline; this plan does not weaken it).
- **A mitigation-system redesign or FedTrace v4.** Multi-Krum's own mitigation behavior is being *measured*, not integrated into or combined with FedTrace v3's own detector logic. FedTrace v3 remains frozen throughout.
- **Unrelated optimization work** (reopening the FedProx/`local_epochs`/SCAFFOLD track, `analysis/FEDTRACE_STAGE_B_FINAL_SYNTHESIS.md` §15) — remains a closed, separate track.

## Final Report

1. **File created:** `research_plans/FEDTRACE_EXTERNAL_BASELINE_SELECTION_PLAN.md`.
2. **Files modified:** none — every source document and codebase file consulted was read-only.
3. **Best direct attribution-baseline candidate:** no fully native, threat-model-appropriate one exists in the literature verified; **Multi-Krum's per-round exclusion pattern**, used as an explicitly-labeled secondary/repurposed proxy, is the best available option (§4, §6, §11). FoolsGold was the closest native candidate but was rejected on fairness grounds (single-non-colluding-attacker mismatch, §4).
4. **Best secondary robust-aggregation candidate:** coordinate-wise median / trimmed mean (Yin et al., ICML 2018) — documented as a viable future second aggregation baseline, not implemented now (§4).
5. **Whether each is apples-to-apples with FedTrace:** no method evaluated is apples-to-apples on FedTrace's own attribution task — Multi-Krum and trimmed mean/median are complementary (robustness, not attribution); FoolsGold would be apples-to-apples in principle but does not fairly apply to this project's single-attacker threat model (§3, §8).
6. **Whether trace-only evaluation is possible:** no — none of the three shortlisted candidates can be evaluated from the already-collected `client_round_trace.csv` files; all require either raw per-client update tensors or must run live as the aggregation rule (§7).
7. **Whether new experiments are required:** yes, for any candidate pursued — Multi-Krum (the selected next task) must run as a live `AggregationStrategy` across new training runs of the same four already-validated attack scenarios plus their paired honest baselines (§7, §11).
8. **Key assumptions of each candidate:** Multi-Krum assumes a known/bounded number of Byzantine clients `f` and `n ≥ 2f+3` (satisfied at `n=5`, `f=1`); trimmed mean/median assumes bounded per-coordinate variance and a known trim fraction; FoolsGold assumes multiple, mutually-similar colluding attackers exist (§3, §5).
9. **Main fairness concern:** every literature candidate that natively performs attribution (FoolsGold) is built around detecting *collusion between multiple* attackers, which does not exist in this project's single-attacker threat model — no clean, fair, native external attribution baseline currently exists for this exact benchmark (§4, §8).
10. **Exact metrics for comparison:** attribution-side (Multi-Krum's repurposed signal only) — predicted client, attribution correctness, first anomaly, confirmation round, onset estimate, onset error, detection delay, honest persistent FP, precision, recall, F1 (§9); aggregation-side (Multi-Krum natively) — final test loss, Top-1, Top-5, degradation relative to attacked FedAvg, clean-performance cost, exposed exclusion pattern (§10).
11. **One baseline task selected next:** **B — implement Multi-Krum as a new `AggregationStrategy`**, evaluated on the same four already-validated attack scenarios plus paired honest baselines (§11).
12. **Publication-risk justification:** Multi-Krum is the field's most standard Byzantine-robust aggregation reference point; benchmarking against it directly answers a reviewer's most likely objection ("why not just use an existing robust method?") and is the single highest-leverage evidence gap identified by the Stage B synthesis (§12, §21 of `analysis/FEDTRACE_STAGE_B_FINAL_SYNTHESIS.md`).
13. **What explicitly should NOT be implemented next:** five aggregators at once, a new attack family, additional seeds, a new dataset/model, a FedTrace v4 or mitigation-system redesign, or any reopening of the FedProx/optimization track (§13).
14. **Confirmation FedTrace v3 unchanged:** confirmed — `src/analysis/fedtrace_detector.py` was not modified.
15. **Confirmation no experiment/config/code/test/database changed:** confirmed — only this one planning document was created; `src/federated/aggregation/`, `src/federated/runner.py`, and every analysis/plan document consulted were read-only.
